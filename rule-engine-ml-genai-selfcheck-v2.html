HYBRID Most production systems end up hybrid — rules for the deterministic core, ML for scoring, GenAI for language — like the precedent below. These gates pick the primary class for a given piece of work, not one winner for the whole system.

▸ why this still needs a caveat
Two different "no"s: the problem might not be defined yet (re-scope), or it might genuinely need more than one class working together — e.g. retrieval and ranking before any generation (decompose, then send each piece back through these gates). And inside a "yes": GenAI narrates and synthesizes well; it's much less reliable at multi-step autonomous reasoning or tool orchestration — keep deterministic control flow in charge of the sequence.
Applies regardless of where you land
The 10x heuristic — not a measured constant
Every path still has to clear this, but calibrate the baseline first. For a permanent production system, the bar is 10x over the alternative you didn't pick. For a one-time task, the honest baseline is a person doing it once by hand — which changes the math completely (see the True Cost tab). Treat 10x as a forcing function to keep you honest, not an empirically derived threshold.
The orthogonality rule — applies specifically when the answer is GenAI
The model narrates, translates, and orchestrates intent — it is not a deterministic executor. It never touches raw data, never does arithmetic, and is never the system of record; even at temperature 0, outputs aren't guaranteed bit-for-bit reproducible. Validated APIs and rules own the computation and sit orthogonal to it. Enforce it at the boundary: require schema-validated structured output, and give the model least-privilege access to any tool it can call.

The gates pick a class. This layer stress-tests that choice against how often it runs, what it really costs, and how it decays — and it can override the gate's answer.

Usage frequency / duration

One-time / rare

Relax the 10x bar. Build cost can never amortize over a single run — default to whatever costs least in engineering time, usually GenAI (or a person). Price-per-call stops mattering when there's only one call.

Periodic (monthly / quarterly)

The ambiguous middle. Favor whatever costs least to keep alive between runs — an idle rule engine is nearly free; an idle ML model still owes you monitoring and may be stale by the next run; a GenAI call needs re-checking against drift first. Batch pricing (~half of real-time) fits this rhythm well.

Continuous / high-volume

Per-call GenAI cost scales linearly with volume; rule/ML marginal cost approaches zero once built. At sustained frequency, a job an LLM could technically do may cost more per month than a deterministic build doing the same job. "Feasible" stops being reason enough.

Model drift

ML model

Data drift: the inputs stop looking like training data. Concept drift: the right answer for the same input changes — usually the more dangerous one. Monitored with statistical distribution tests and champion/challenger evaluation before a new model is promoted. A permanent line item, not a one-time cost.

GenAI

The model changes underneath you — providers update or retire versions on their own schedule. Same prompt, different output, no code change on your side; documented cases show accuracy on identical questions swinging by tens of points across a single update. Managed with prompt-regression testing against a maintained golden dataset, version pinning, and a deprecation calendar with an owner.

Rule engines: no drift. Behaviour changes only when a person edits a rule — the lowest ongoing model-risk burden of the three.

For a regulated bank, these aren't optional context — they can add real cost and lead time to the ML/GenAI paths, and are worth checking before you commit.

Model risk management
IFDoes this inform a decision about a customer, credit, or risk/compliance outcome?
THENFull model inventory, independent validation, documented conceptual soundness, and ongoing monitoring apply — landing far more heavily on ML and GenAI than on a deterministic rule engine.
▸ why this still needs a caveat
SR 11-7 / OCC 2011-12 territory — supervisory guidance with a deliberately broad model definition that examiners apply to statistical, ML, and GenAI systems alike. Scope depends on use, not technology: an LLM helping staff search internal documents is generally not a "model" under this guidance; one that generates credit-risk narratives or classifies complaints for regulatory reporting almost certainly is. Validation and documentation add real calendar time before a decision-facing capability can ship — budget for it up front, and confirm specifics with your MRM and legal functions.
Adverse action
IFCould this drive a customer-facing decision that's adverse — declined, reduced, or changed terms?
THENSpecific, accurate reasons are legally required. The model may narrate the reason; the reason itself has to come from a validated, explainable decision system.
▸ why this still needs a caveat
ECOA / Regulation B territory, reinforced by CFPB guidance: creditors can't excuse noncompliance on the grounds that their technology is too complicated or opaque to understand. Practically — wrap opaque models with a validated explainability layer, log reason-code accuracy, and never let the LLM freelance the actual reason, only the phrasing.
Data residency
IFDoes this touch non-public personal or financial data through a third-party-hosted GenAI API?
THENNeeds contractual residency guarantees, data minimisation or tokenisation before the prompt leaves your environment, or route to on-prem rules / self-hosted ML instead.
▸ why this still needs a caveat
Every inference call is a small transfer of sensitive data to someone else's infrastructure — sovereignty rules can apply even to that ephemeral pass-through. Major providers now sell regional-processing tiers at roughly a 10% premium; that premium is the price of the guarantee, not a reason to skip it for a genuinely sensitive workload.
Lock-in & prompt injection
IFIs this a GenAI path with logic tuned to one provider's model, or with any tool-calling ability?
THENTwo risks worth designing against from day one: switching providers later is expensive if logic is baked into one model's quirks, and the model can't reliably tell trusted instructions apart from untrusted text it reads.
▸ why this still needs a caveat
Lock-in: keep model choice behind an abstraction layer, enforce structured output, and maintain a provider-neutral test set so switching is a config change, not a rewrite. Injection: OWASP's top-ranked LLM risk for a reason — no fool-proof prevention exists yet, so never give the model direct write access to systems of record, treat anything it reads as untrusted, and enforce least-privilege on every tool it can call.
Already shipped this way

Wire-transaction matching

A deterministic rules engine — normaliser, rule registry, pairwise evaluation, confidence filtering — identifies related transactions. The model's only job is turning that rule-match metadata into a plain-language explanation. Zero LLM arithmetic. Zero LLM data retrieval. Fully deterministic, fully testable.
